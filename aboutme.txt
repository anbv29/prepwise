PREPWISE — COMPLETE PROJECT AND CODE WALKTHROUGH
================================================

Purpose of this document
------------------------
This file explains what Prepwise is, how the complete system works, why it was designed this way, what every source/configuration/test file is responsible for, which OOP and system-design ideas are used, the important security decisions, current limitations, and interview questions you should be ready to answer.

The original assignment PDF is the source of the product requirements. It asks for an AI Interview Prep Kit that accepts a job description, a company URL, and the number of preparation days; performs company and public interview research; creates requirements, questions, flashcards, coverage, and an exact-day schedule; supports editing, regeneration, practice, authentication, persistence, and a machine-readable batch evaluator. Prepwise is the implementation of that brief.


1. WHAT TYPE OF PROJECT IS THIS?
--------------------------------
Prepwise is a full-stack, AI-assisted interview preparation SaaS application. It is also a research pipeline and a small job-processing system.

From a product point of view, a candidate pastes a job description and company URL, chooses how many days remain before the interview, and receives a structured preparation kit. The kit contains:

- a researched company brief with source links;
- normalized must-have and nice-to-have role requirements;
- categorized interview questions with difficulty and requirement references;
- flashcards linked to requirements;
- a day-by-day schedule whose length exactly matches days_available;
- a deterministic coverage report showing whether every requirement is addressed;
- an editable builder, selective regeneration, and confidence-based practice.

From a technical point of view, it combines:

- a Next.js single-page-style web experience;
- an Express REST API;
- MongoDB persistence;
- cookie/session authentication;
- an asynchronous persistent generation queue;
- safe web crawling and optional public-discussion search;
- OpenAI or Gemini structured generation;
- deterministic validation, repair, coverage, and scheduling;
- a separate evaluator CLI for automated grading.

3. HIGH-LEVEL ARCHITECTURE
--------------------------

The dependency direction is:

Browser UI -> API client interface -> Express HTTP routes -> application services
           -> repositories -> MongoDB
           -> generation worker -> pipeline -> LLM/research adapters
                                      -> deterministic coverage/schedule

The monorepo boundaries are:

- apps/web: user interface only;
- apps/api: HTTP, authentication, orchestration, jobs, and deployment runtime;
- packages/contracts: the shared truth for the required JSON shapes;
- packages/database: persistence schemas, indexes, and repository classes;
- packages/pipeline: research, AI generation, repair, coverage, scheduling, and batch evaluation;
- scripts: evaluator and production-environment validation;
- tests: repository-level CLI/scaffold fixtures and tests.

This separation matters because the evaluator can run the pipeline without the browser or Express, the API can switch AI/search providers without changing routes, and database mechanics do not leak into business rules.


4. END-TO-END REQUEST FLOW
--------------------------

Account flow
1. The browser validates login or registration data.
2. POST /api/auth/register or /api/auth/login sends credentials to the API.
3. Passwords are never stored. Registration creates a salted scrypt hash.
4. A random session token is returned only in a secure HTTP-only cookie; MongoDB stores only its SHA-256 hash.
5. Private routes authenticate the cookie and always query kits/jobs by both resource ID and owner ID.

Kit creation flow
1. The browser validates the job description, company URL, and days.
2. It sends POST /api/kits with an idempotency key.
3. The API fingerprints the normalized input, creates a draft kit plus a queued job, and immediately returns pollable IDs.
4. The generation progress page polls the job/kit. The expensive work is not tied to one long browser request.
5. A worker atomically claims the oldest eligible job and increments its attempt counter.
6. The worker checks the owner plan. Free users use the standard generator; paid users may use the grounded-search generator.
7. Progress and warnings are persisted as stages complete.
8. On success, the validated kit and completed job are written together logically. On failure, a structured retryable/non-retryable error is saved on both records.

Generation pipeline
1. Extract atomic role requirements from the untrusted job description.
2. In parallel, crawl a small ranked set of company pages and, when entitled/configured, search public interview discussions.
3. Generate the company brief with only known source IDs.
4. Generate categorized questions and normalize all references/IDs.
5. Compute coverage in code. If a must-have is uncovered, make one targeted AI repair pass and recompute. Fail closed if the repair still does not cover it.
6. Generate flashcards and perform the same must-have coverage repair.
7. Build the exact number of schedule days deterministically, putting must-have and harder work earlier.
8. Assemble the result and run the complete Appendix A KitSchema before returning it.

Editing and regeneration flow
1. Editing happens through KitEditorContext.
2. The UI marks directly changed questions as edited and updates the React Query cache optimistically.
3. PATCH /api/kits/:kitId persists a schema-valid kit. A mutation sequence prevents an older response from overwriting a newer edit.
4. Before regeneration, the dialog requests a preview of preserved/replaced counts.
5. Category regeneration keeps edited questions, replaces only unprotected items in that category, remaps references to the current requirement IDs, avoids ID collisions, and rebuilds coverage/schedule.

Practice flow
1. The browser loads the kit and the owner's saved practice progress.
2. Cards are copied and sorted by confidence; unseen cards act as score zero and therefore appear first.
3. The user reveals the answer and rates confidence from 1 to 4.
4. Progress updates optimistically and is persisted owner-by-owner in MongoDB.
5. The next session again prioritizes unseen and low-confidence material.


5. WHY SOME WORK IS AI AND SOME IS DETERMINISTIC
-------------------------------------------------
AI is good at interpreting natural-language job descriptions and producing tailored explanations, questions, and flashcards. It is not the correct authority for invariants such as unique IDs, valid references, complete must-have coverage, or an exact number of schedule days.

Therefore:
- the model proposes semantic content;
- Zod constrains its response shape;
- normalization code assigns application-owned stable IDs and discards unknown references;
- coverage is computed from references in ordinary TypeScript;
- the second pass is triggered by that computed result, not by the model claiming it covered everything;
- scheduling is a pure deterministic algorithm;
- the final schema is the last gate before persistence/output.

This is one of the project's strongest design decisions: generative work remains flexible, while correctness properties remain testable and repeatable.


6. OOP, SOLID, AND CODE-DESIGN PRINCIPLES USED
----------------------------------------------

This codebase uses pragmatic TypeScript OOP. It does not create deep class hierarchies merely to look object-oriented. It favors small classes at stateful/integration boundaries and pure functions for transformations.

Encapsulation
- UserRepository, KitRepository, GenerationJobRepository, ResearchCacheRepository, and PracticeProgressRepository hide Mongo query details and validate their own reads/writes.
- AuthenticationService owns the rules for registration, login, session issue, authentication, and logout.
- OpenAiStructuredLlmProvider and GeminiStructuredLlmProvider hide SDK-specific calls, retry rules, and error translation.
- SafeResearchFetcher owns redirect, size, content-type, timeout, and address-policy enforcement.

Abstraction and polymorphism
- StructuredLlmProvider is a common port. Generation logic depends on the interface rather than directly on OpenAI or Gemini.
- DiscussionSearchProvider allows Brave Search and Gemini Grounding to satisfy the same capability.
- KitGenerator allows the full generator, scaffold generator, and test fakes to be substituted.
- ApiClient lets the web UI switch between real and mock backends without changing components.

Composition over inheritance
- runtime.ts constructs concrete providers, repositories, services, pipeline functions, and the Express app, then injects their dependencies.
- The generator is assembled from research and LLM capabilities rather than subclassing a large base generator.
- Tests pass small fakes/stubs instead of inheriting from production classes.

Single Responsibility Principle
- password.ts hashes and verifies passwords only.
- coverage.ts calculates coverage only.
- schedule.ts schedules only.
- url-policy.ts decides whether a URL/address is safe.
- content.ts extracts bounded useful text.
- HTTP files translate requests/responses, while services own application behavior.

Open/Closed Principle
- Another LLM provider or search provider can be added behind the existing interfaces without rewriting the pipeline.
- A mock ApiClient is added alongside the real client without branching inside every component.

Liskov Substitution Principle
- Implementations of StructuredLlmProvider, DiscussionSearchProvider, KitGenerator, and ApiClient obey the same input/output behavior, so test doubles and real implementations can replace one another.

Interface Segregation Principle
- AuthenticationService accepts narrow repository contracts instead of an all-purpose database object.
- Pipeline stages receive only the provider/research functions they need.

Dependency Inversion Principle
- High-level generation and auth rules depend on interfaces/functions. SDKs and MongoDB sit at the edges.

Other patterns
- Repository pattern: all Mongo access is centralized in repository classes.
- Strategy/Adapter pattern: LLM, discussion search, and browser API clients are replaceable adapters.
- Composition Root/Factory: apps/api/src/runtime.ts creates and wires the production object graph.
- State machine: kit and job schemas restrict valid queued/generating/ready/failed states.
- Cache-aside: research-cache.ts checks Mongo first, otherwise fetches and stores a bounded result.
- Optimistic concurrency/UI: React Query applies edits immediately and rolls back failed mutations; save sequence numbers reject stale responses.
- Idempotent command: kit creation uses an idempotency key plus input fingerprint.
- Producer/consumer queue: HTTP creates work; the worker claims and executes it.
- Fail-closed validation: invalid AI output, unknown references, or unrepaired must-have coverage cannot silently become a successful kit.


7. SYSTEM-DESIGN PRINCIPLES
---------------------------

Clear boundaries
The UI, transport, domain contracts, persistence, generation, and external providers are separated. This reduces coupling and gives each layer a focused test surface.

Asynchronous work
AI plus crawling can take much longer than an HTTP request. Persisted jobs allow immediate acknowledgement, progress polling, retry, stale-job recovery, and server restarts without pretending generation is instant.

Idempotency
A repeated create request with the same owner, key, and fingerprint returns the existing result. Reusing the key for different input is rejected. This prevents duplicate kits after double clicks, refreshes, or network retries.

Consistency and invariants
Mongo documents are parsed through Zod. Ready kits must contain a valid final kit; failed jobs must contain an error; complete jobs must report 100%; references must point to existing IDs; schedule length must equal days_available.

Ownership/multi-tenancy
Private repositories query by ownerId plus object ID. Knowing another Mongo ObjectId is not enough to read or update that user's data.

Graceful degradation
Secondary research failures become warnings when useful generation can continue. The root company page is essential, but child-page/discussion failures can be recoverable. Free users intentionally skip public discussion grounding without showing a fake error.

Bounded resources
Crawl page count, redirects, response bytes, extracted text, timeouts, retry count, job attempts, and input lengths all have limits. Bounds protect cost, latency, memory, and reliability.

Determinism where correctness matters
Stable IDs, coverage reports, reference checks, ordering, and schedules are repeatable. This makes automated grading and regression testing possible.

Observability for users
Persisted stage names, percentages, messages, warnings, error codes, and retryability make the pipeline inspectable rather than leaving a spinner with no explanation.

Deployment topology
Production uses two Vercel projects. Next.js handles the frontend and rewrites same-origin /api calls to the API origin. Express is packaged as the API serverless function. MongoDB provides durable shared state. Secrets remain server-side.


8. SECURITY DESIGN
------------------

- Passwords use salted scrypt, not reversible encryption and not plain SHA hashing.
- Session tokens have high entropy; only their SHA-256 hashes are stored.
- Cookies are HTTP-only, SameSite=Lax, and Secure in production.
- Login uses the same public error for unknown email and wrong password, with a dummy hash verification to reduce user-enumeration/timing leakage.
- State-changing requests reject untrusted browser origins.
- CORS is restricted to the configured web origin.
- JSON bodies are capped at 1 MB.
- Security headers disable framing, MIME sniffing, unnecessary browser permissions, and cross-origin opener access.
- All HTTP, database, AI, file, and form boundaries are validated.
- Prompt instructions explicitly label job descriptions, page text, and snippets as untrusted data rather than system instructions.
- Research accepts only HTTP(S), rejects credentials/nonstandard ports in production, resolves DNS, blocks private/loopback/link-local/reserved/metadata addresses (IPv4 and IPv6), revalidates every redirect, and pins the connection to the validated address to resist DNS rebinding.
- Research accepts only known text content types and enforces declared and streamed byte limits.
- Search keys and LLM keys are read only from server environment variables.
- Output citations are mapped from application-known source IDs, so the model cannot invent arbitrary source URLs.

10. IMPORTANT TRADE-OFFS AND CURRENT LIMITATIONS
------------------------------------------------

1. Two Vercel projects increase setup work but keep web and API responsibilities clear. A single Next.js app could simplify deployment but would require moving/rewriting the Express boundary.

2. The Mongo-backed queue is adequate for an assignment and light workloads. A serious production scale would use a dedicated queue/worker platform with leases, dead-letter handling, concurrency control, and stronger delivery guarantees.

3. Vercel waitUntil is best-effort within serverless execution limits. Long jobs can still approach function duration. The persisted job design makes migration to a dedicated worker possible.

4. Research is intentionally small and bounded. This improves safety/cost/latency but may miss deeply nested company information.

5. Free users receive all core Gemini generation and company crawling but skip public interview-discussion grounding. Paid entitlement exists in the backend model, but payment/checkout and self-service plan upgrades are not implemented; pricing buttons are intentionally non-purchasing UI.

6. Gemini Google Search grounding depends on account billing/quota. The UI hides that specific warning as requested, while the backend retains the diagnostic.

7. The UI/API creation form currently caps days at 30, while the core schedule algorithm and its tests support 60 days as requested by the evaluator edge case. If 60-day interactive plans are required, raise the HTTP/UI maximum consistently.

8. The evaluator's environment generator currently constructs OpenAI directly, whereas the web/API runtime can select Gemini. To evaluate with Gemini, refactor the CLI to reuse provider selection from runtime/config.

9. Frontend kit types partially duplicate the shared contract types. This offers UI convenience but can drift. A later cleanup should derive base types directly from @prep-kit/contracts and add only UI extensions.

10. The code has registration/login/session/logout but no email verification, password reset, OAuth, CSRF token scheme, abuse rate limiting, audit log, or account deletion. These are production SaaS concerns outside the assignment's core scope.

11. Company URLs may refuse bots, require JavaScript, or block hosting-provider IPs. The system reports research gaps honestly instead of inventing facts.

12. A real deployment is not complete until Vercel SSO/protection is disabled for public access, Mongo Atlas credentials/network access work from Vercel, environment variables are set for Production/Preview as intended, the API /api/health succeeds, registration/login work, and a real generated kit reaches ready state.

13. Secrets previously pasted into chat or logs should be rotated. Never copy real keys into this file, source code, Git, screenshots, or NEXT_PUBLIC_ variables.


11. HOW TO EXPLAIN THE PROJECT IN ONE MINUTE
--------------------------------------------

“Prepwise is a full-stack AI interview-preparation platform. A user supplies a job description, company URL, and available days. The API creates an idempotent persistent job, then a worker safely crawls relevant company pages, optionally searches attributable interview discussions for paid users, and uses a provider-neutral OpenAI/Gemini pipeline to extract requirements and generate a brief, questions, and flashcards. The model never decides correctness by itself: stable references, must-have coverage, the targeted second pass, exact-day scheduling, and the final output shape are enforced deterministically with TypeScript and Zod. Users can edit and reorder content, selectively regenerate without losing protected edits, and practice low-confidence cards first. MongoDB provides owner-isolated persistence, sessions, jobs, cache, and progress. The same core pipeline is exposed through the required batch-evaluation CLI.”


12. INTERVIEW QUESTIONS AND ANSWER POINTS
-----------------------------------------

1. Why did you use a monorepo?
Answer points: shared contracts; atomic changes across UI/API/pipeline; one install/test command; still keeps deployable boundaries.

2. Walk me through a kit request from button click to final result.
Answer points: client validation -> idempotent POST -> draft/job -> atomic claim -> plan-aware generator -> research/LLM -> repair -> deterministic schedule/coverage -> final schema -> polling UI.

3. Why not call Gemini directly from the browser?
Answer points: secret exposure, no trusted authorization/entitlement, CORS/control, inability to enforce output/schema/retries centrally, no durable jobs.

4. Why use a background job instead of one synchronous endpoint?
Answer points: variable AI/research latency, browser disconnects, progress, retry, stale recovery, duplicate prevention, future worker scaling.

5. How does idempotency work?
Answer points: owner + idempotency key unique; canonical input fingerprint; same request returns original; different input with same key is conflict.

6. What happens if kit insertion succeeds but job insertion fails?
Answer points: compensating deletion removes the unusable draft; explain this is application-level compensation, not a multi-document transaction.

7. How do you stop two workers from processing one job?
Answer points: atomic find-and-update claim of oldest queued eligible job; status/attempt predicate; Mongo index supports it.

8. How do you recover a crashed worker?
Answer points: startedAt/stale threshold; recover stale generating jobs; requeue below attempt limit or mark failed.

9. Why Zod when TypeScript already exists?
Answer points: TypeScript disappears at runtime; network/database/model/file input is unknown; Zod validates and infers types.

10. How do you guarantee the output follows Appendix A?
Answer points: stage schemas, normalization, reference filtering, deterministic invariants, final KitSchema parse before save/output.

11. How is the second coverage pass genuine?
Answer points: compute coverage in code from stable requirement IDs; collect uncovered must-haves; send only that repair target; merge; recompute; fail closed if still uncovered.

12. Why is scheduling deterministic?
Answer points: exact counts/ordering are invariants, not creative language tasks; deterministic function is cheap, repeatable, testable, and cannot hallucinate IDs.

13. How is the exact number of days guaranteed?
Answer points: validate positive integer; create exactly N buckets numbered 1..N; distribute ranked work; review-only days for excess; schema cross-check.

14. How are harder/must-have topics put earlier?
Answer points: priority/difficulty scoring, stable sort, balanced assignment, test asserts expected ordering.

15. How do you prevent hallucinated citations?
Answer points: crawler owns URLs and assigns source IDs; model may select only IDs; server maps back and removes unknown IDs.

16. How do you defend against prompt injection in scraped pages/JDs?
Answer points: system/developer-style instruction declares content untrusted data; delimit/bound it; model output constrained; server independently validates/recomputes.

17. How do you prevent SSRF?
Answer points: protocol/port/credential rules, DNS resolution, private/reserved/metadata blocking for v4/v6, redirect revalidation, IP pinning, production disables escape hatch.

18. Why respect robots.txt?
Answer points: responsible crawling, site policy compliance, bounded access; blocked pages become provenance-aware gaps rather than bypass attempts.

19. Why cache research failures?
Answer points: avoid hammering an unavailable URL/provider; short failure TTL allows recovery; preserve retryability and error detail.

20. How is user data isolated?
Answer points: auth middleware resolves session owner; repository reads/updates use both ownerId and resource ID; tests assert scoping.

21. How are passwords and sessions protected?
Answer points: salted memory-hard scrypt; timingSafeEqual; high-entropy cookie token; database stores SHA-256 token hash; expiry TTL; HTTP-only/Secure/SameSite.

22. How do free and paid plans differ?
Answer points: core generation/crawl for free; worker selects grounded generator only from server-stored paid plan; client cannot self-declare entitlement.

23. How does selective regeneration preserve edits?
Answer points: edited flag, target category only, preview, preserve protected IDs/content, remap current requirement references, avoid collisions, rebuild dependent schedule/coverage.

24. How do optimistic edits remain safe?
Answer points: snapshot previous cache, apply local clone, send PATCH, rollback error, mutation sequence prevents stale response overwrite.

25. Why freeze flashcard order for one practice session?
Answer points: saving confidence should not reshuffle the card currently being studied; new priority applies next session, giving predictable UX.

26. What is the most useful design pattern here?
Answer points: provider/strategy plus dependency injection; same pipeline works with OpenAI, Gemini, and fakes; testability and migration.

27. Why composition over inheritance?
Answer points: capabilities vary independently; avoids rigid base classes; functions/classes receive only required collaborators.

28. How do you handle partial external failure?
Answer points: structured errors with retryability; root research vs optional child sources; partial discussion results/warnings; no silent fabricated research.

29. What would you change for 100,000 users?
Answer points: dedicated queue/workers, concurrency/rate quotas, Redis/cache tier, streaming/event progress, observability/tracing, per-tenant limits, backpressure, replicas/index review, object storage for batch output.

30. What would you monitor in production?
Answer points: job time by stage, queue age/depth, success/retry/failure codes, provider latency/tokens/cost, crawl failures, coverage repairs, Mongo latency, auth errors, Vercel duration, cache hit rate.

31. Why two Vercel projects?
Answer points: independent framework/runtime builds and env variables; frontend same-origin proxy retains cookie-friendly API calls; downside is configuration complexity.

32. What tests give the highest confidence?
Answer points: schema cross-field tests, SSRF/redirect/byte-limit tests, coverage/schedule edge tests, worker free/paid/state tests, auth ownership HTTP tests, evaluator end-to-end test.

33. What is currently the largest technical debt?
Answer points: serverless background-work reliability, duplicated frontend types, evaluator provider selection mismatch, 30-day interactive cap versus 60-day core capability, missing billing/abuse controls.

34. If the AI provider returns malformed JSON, what happens?
Answer points: provider parses/validates; retry within bound for recoverable malformed output; structured error after exhaustion; no invalid kit is persisted as ready.

35. Why use stable application IDs instead of model-generated IDs?
Answer points: predictable references, collision/duplicate control, reproducible coverage/schedule, safe merging/regeneration, easier tests.

36. How would you add another model provider?
Answer points: implement StructuredLlmProvider, add validated config/factory branch, keep stage/pipeline logic unchanged, add contract/error/retry tests.

37. How would you add Stripe subscriptions safely?
Answer points: hosted checkout, verified webhook as source of truth, server-side plan repository update, idempotent event storage, never trust browser plan, entitlement tests.

38. What was your most defensible product/engineering decision?
Answer points: keep semantic generation in AI but make coverage, references, schedules, authorization, and output validity deterministic and server-controlled.

39. What happens when a company blocks crawling?
Answer points: structured research warning/no-research brief; do not fabricate; still generate from JD where possible; show attributable sources only.

40. What would you build next?
Answer points: production-grade queue, billing, email verification/reset, rate limiting, richer observability/evals, derived shared UI types, provider parity in evaluator, accessibility/browser E2E tests.


13. FINAL SUMMARY
-----------------
Prepwise is best described as a reliability-focused AI product. The visible result is an interview kit, but the engineering value is in the boundaries around the AI: safe source collection, structured provider adapters, durable asynchronous work, schema/state invariants, deterministic coverage and schedules, preserved human edits, secure owner isolation, and automated evaluator output. In an interview, emphasize not only what the model generates, but how the system proves that the generated result is usable, attributable, complete, and recoverable.
